Real-time collaborative editor

like Google Docs

Many people type into the same document at once, every keystroke must feel instant, and everyone must end up with the same text. Give each document one single-threaded session that puts all edits in one order, and have every client transform its own unacknowledged edits around whatever arrives.

Requirements and scale

  • 50M daily users, about 5M documents open at peak, usually 1 to 5 editors on each.
  • About 1M operations a second in total, but only a handful per second on any one document. The load is millions of small independent streams, so shard by doc_id.
  • Your own typing shows immediately. Other people's edits and cursors show within 200 ms at p95.
  • No acknowledged edit is ever lost. Full version history is kept.
  • Cap live editors at about 100 per document. Extra readers get a view-only stream.

Architecture

  1. The client applies the keystroke to its local copy at once, then sends the operation tagged with the revision it was typed against.
  2. A gateway asks the directory which host owns this document and forwards the operation. Gateways hold sockets and no document state.
  3. The doc session transforms the operation against anything committed since its base revision, gives it the next revision number, appends it to the op log, and only then acknowledges.
  4. The session sends the committed operation back through the gateways to every other client on the document. Each client transforms it against its own unacknowledged edits before applying.
  5. Opening a document reads the latest snapshot plus the short log tail after it. A snapshot is written every 1,000 operations.

Data model and API

WS /docs/{doc_id}
  -> open(last_rev)                     <- snapshot, ops after last_rev
  -> op(client_id, seq, base_rev, op)   <- ack(rev)
                                        <- op(rev, author, op)
  -> cursor(range)                      <- cursors[]   (never stored)

ops        (doc_id, rev) -> op, author, client_id, seq, ts
snapshots  (doc_id, rev) -> blob key
docs       doc_id        -> owner, acl, head_rev, lease_epoch

The hard part: two edits made against the same revision

Without the transform, the server would apply B's del(2) to XABC and remove the letter B. A and the server would hold XAC while B holds XAB, and the copies would never agree again.

The client rule: keep at most one operation in flight, buffer the rest, and transform every incoming operation against the in-flight one and the buffer. The server applies the mirror rule against everything committed after the operation's base revision. One thread per document means there is exactly one history to transform against.

Reconnects reuse the same machinery. The client resends anything unacknowledged with the same (client_id, seq), and the session drops duplicates.

Trade-offs

Operational transform with a central sequencer over CRDTs

CRDTs such as Yjs or Automerge need no central order, which is what you want for offline-first or peer-to-peer editing. Here a server is already required for auth, access control and storage, so let it also decide order. The document then carries no per-character metadata.

One session process per document over many writers coordinating through the database

A single writer gets a total order with no locks. One document's throughput is bounded by how fast people type, so one thread is plenty.

Append-only op log plus snapshots over saving the latest document

Appends are cheap and durable, and the log gives version history, undo and reconnect replay for free. The cost is a compaction job and a slower cold open if snapshots fall behind.

WebSockets over polling or server-sent events

Edits flow both ways several times a second. Sticky connections are the price, and the gateway tier exists to pay it.

Failure modes

  • The session host dies. Its lease in the directory expires and the next operation lands on a new host, which rebuilds from the latest snapshot and the log tail. Clients resend unacknowledged operations. Nothing acknowledged is lost because the ack comes after the append.
  • Two hosts both believe they own the document. Every append is conditional on rev = head_rev + 1 and carries the lease epoch. The stale host's write fails and it shuts its session down.
  • A client was offline for an hour. It reopens with its last_rev. If the log still covers that range it replays the tail, otherwise it loads a snapshot and rebases its pending edits.
  • Five thousand people open one document. Editors stay on the session. Viewers move to a read-only tier that subscribes to the committed stream.

Staff additions

Cut from version one
Offline editing, comments and suggestions, embedded objects. Version one is plain text, 10 editors per document, one region.
Migration path
From an editor that saves the whole document: start writing the op log beside the existing saves, compare the replayed document with the saved one every night, then switch reads to snapshot plus log.
Monitor and page on
Op acknowledgement latency at p99, session failovers per minute, and checksum mismatches. Clients send a hash of their text at revision N every few seconds, and any mismatch pages someone because it means copies have diverged.

Sheet 02 of 20System design

Video streaming platform

like YouTube

This is two systems that share a database. Upload is a slow, heavy, retryable pipeline that turns one file into thousands of small ones. Playback is almost all of the traffic and should never reach your servers: it is immutable files on a CDN, with the player choosing the quality.

Requirements and scale

  • 500 hours of video uploaded every minute and 1 billion hours watched a day. Reads outnumber writes by several thousand to one.
  • An upload is watchable at low resolution within a few minutes. Higher resolutions follow.
  • Playback starts in under 2 seconds and adapts to the viewer's bandwidth without stalling.
  • Each source hour becomes about 6 renditions. New storage runs to petabytes a day, so codec choice and storage tiers are cost decisions.
  • Uploads survive flaky mobile networks. Any part can be retried without restarting.

Architecture

  1. The creator app asks for an upload session and sends the file in parts. Any part can be retried on its own.
  2. Parts land in object storage.
  3. Completing the upload puts an event on the job queue.
  4. Transcoders take the job, split the source into short chunks and encode every chunk at every resolution in parallel.
  5. Finished segments and manifests are written to the origin store under immutable names.
  6. The video is marked ready as soon as the lowest renditions exist.
  7. A viewer opens the watch page. The API returns metadata and the manifest URL.
  8. The player fetches segments from the nearest CDN edge. The edge pulls from origin only on a miss, so a popular video stops touching origin after its first few views.

Data model and API

POST /uploads                 -> upload_id, presigned part URLs
PUT  {part URL}               -> etag          (retry any part)
POST /uploads/{id}/complete   -> video_id, state = PROCESSING
GET  /videos/{id}             -> metadata, manifest URL
GET  cdn/{video}/{rung}/{n}.m4s                (immutable, cache forever)

videos      video_id -> owner, title, state, duration, manifest_key
renditions  (video_id, rung) -> codec, bitrate, state
view events -> stream -> counters              (never in the request path)

The hard part: transcoding as thousands of small retryable tasks

A one-hour source cut into 4-second chunks is 900 chunks. At six renditions that is 5,400 encode tasks that do not depend on each other. Any worker can take any task, and the output key video/rung/chunk makes a repeated task harmless.

Chunks are cut on keyframe boundaries at the same timestamps in every rendition. That alignment is what lets the player switch resolution between two segments without a visible glitch.

Adaptive bitrate lives in the player. The manifest lists every rendition, the player measures download speed and buffer depth, and it picks the rendition for the next segment. The server side stays plain cacheable HTTP.

Trade-offs

HTTP segments behind a CDN (HLS or DASH) over a stateful streaming protocol

Segments are ordinary immutable files, so every CDN and browser cache works unchanged and scaling playback becomes the CDN's job. The cost is a few seconds of latency, which does not matter for on-demand video.

Chunked parallel transcode over one long encode per file

Time to first playable frame drops from the length of the video to a few minutes, and a worker crash costs one 4-second chunk. The cost is split and stitch logic and keeping keyframes aligned.

Cheap codec for everything, better codecs for hits over every video in every codec

Most uploads get few views. Encode all of them in H.264, then add AV1 or VP9 once a video crosses a view threshold. Compute goes where it saves the most bandwidth.

View counts from an event stream over a counter updated in the request path

Counts can lag by seconds. Playback must never wait on a write.

Failure modes

  • An upload drops at 90%. The upload session lists which parts arrived. The app resends only the missing ones.
  • A transcoder dies mid-task. The queue's visibility timeout hands the task to another worker. Output keys are deterministic, so the retry overwrites the partial file.
  • A video goes viral on a cold cache. Thousands of edges miss at once. A regional origin shield collapses those into one fetch per segment.
  • The origin region is lost. Manifests and popular segments are replicated across regions. Cold long-tail videos are re-encoded from the replicated raw file when someone asks for them.

Staff additions

Cut from version one
Live streaming, multiple codecs, recommendations, comments. Version one is upload, one H.264 ladder, play.
Migration path
From serving single MP4 files: build the segmented ladder for new uploads first, backfill old videos in order of views, and keep the MP4 as a fallback rendition until the backfill covers most watch time.
Monitor and page on
Time from upload complete to first playable rendition at p95, transcode queue age, video start time and rebuffer ratio by region, CDN hit ratio. Page on queue age and on a regional jump in rebuffering.

Chat with read receipts

like WhatsApp

Most recipients are offline when a message is sent, yet it must arrive once, in order, on their device. The server is a store-and-forward relay: write the message to the recipient's inbox, deliver it when a socket exists, delete it when the device acknowledges. Read receipts are small messages travelling the other way along the same path.

Requirements and scale

  • 2 billion users and about 100 billion messages a day. That is 1.2M a second on average and three times that at peak.
  • Hundreds of millions of open connections. One chat server holds about 1M sockets, so the fleet is hundreds of servers that do little except hold connections.
  • Delivery between two online phones in under 200 ms. Messages for an offline phone are kept for 30 days.
  • Messages are end-to-end encrypted. The server stores ciphertext it cannot read, and only until delivery.
  • Order matters within a conversation. No global order is needed.

Architecture

  1. Phone A sends the encrypted message with a client_msg_id over its open socket.
  2. Chat server A writes it to B's inbox, then acknowledges. That acknowledgement is the single tick, and it means the server has stored the message.
  3. Server A asks the session registry which chat server holds B's socket.
  4. It forwards the message to that server. If B has no live socket, the message waits in the inbox, a push notification wakes the phone, and B drains its inbox on reconnect.
  5. Chat server B writes the message to B's socket.
  6. B's device acknowledges. The inbox entry is deleted and a "delivered" receipt starts the same journey back to A.

Data model and API

WS frames
  -> send(chat_id, client_msg_id, ciphertext)   <- ack(msg_id, ts)
  <- deliver(msg_id, chat_id, from, ciphertext) -> ack(msg_id)
  -> receipt(chat_id, delivered | read, upto_msg_id)
  <- receipt(chat_id, user, delivered | read, upto_msg_id)

inbox       (user_id, msg_id) -> envelope     delete on ack, TTL 30 d
chat_state  (chat_id, user_id) -> delivered_upto, read_upto
sessions    user_id -> chat server, device     TTL, renewed by heartbeat
msg_id is time-sortable, so order in a chat = sort by msg_id

The hard part: what each tick proves

A receipt is a watermark for one chat: "delivered up to m1" or "read up to m1". Opening a chat with 40 unread messages sends one receipt. A row per message per reader would multiply write volume and add nothing.

Status only moves forward: pending, sent, delivered, read. A late or duplicated receipt carrying an older watermark is ignored, so receipts need no ordering guarantee of their own.

In a group the server keeps delivered_upto and read_upto per member. The sender sees two ticks when the lowest watermark across members passes the message, and can ask for the per-member list.

Privacy settings are enforced where the receipt is produced. A device with read receipts turned off never emits the read watermark.

Trade-offs

A per-user inbox, deleted on ack over a permanent per-chat log on the server

The recipient is usually offline and reconnects needing one thing: everything addressed to it. With end-to-end encryption the server has no use for history either. The cost shows up with multiple devices, because each device becomes its own recipient with its own inbox.

At-least-once delivery with client dedupe over exactly-once delivery

A lost ack causes a resend, and the client drops any msg_id it has already shown. Exactly-once across a mobile network cannot be bought.

Direct server-to-server forward with the inbox as fallback over routing every message through a broker

The inbox already holds the durable copy, so the forward can be a plain RPC that is allowed to fail.

Receipts as watermarks over a receipt per message

One small write per chat open, and old or duplicate receipts are harmless.

Failure modes

  • A chat server crashes. A million clients reconnect to other servers with jittered backoff. Their registry entries expire by TTL. Every undelivered message is still in an inbox.
  • The registry is stale. Server A forwards to a server that no longer holds B. It answers "not here", and the message waits in the inbox until B reconnects.
  • A delivery ack is lost. The message is delivered again on the next drain. The client dedupes on msg_id.
  • A phone is off for a month. Its inbox entries expire after 30 days. The sender stays on one tick.

Staff additions

Cut from version one
Groups, media, multiple devices, last seen. Version one is one-to-one text with ticks.
Monitor and page on
Send-to-delivered latency at p99 for pairs who are both online, inbox depth and the age of the oldest entry, connections per server, reconnect rate. Page on a reconnect storm and on inbox age growing for users who are online.

Ride hailing

like Uber or Ola

Two problems hide in this one. Driver locations are a write-heavy index that goes stale in seconds, and matching must hand each driver to exactly one rider even when thousands of requests land together. Keep locations in memory keyed by map cell, and make the change to a driver's state a compare-and-set.

Requirements and scale

  • 5M drivers online at peak, each reporting position every 4 seconds. That is 1.25M location writes a second.
  • About 30M trips a day. Ride requests peak at a few thousand a second, small next to location writes.
  • A rider sees a matched driver within about 10 seconds. The nearby-drivers query answers in under 100 ms.
  • A driver is never offered two trips at once. A trip is never lost once the rider has seen it confirmed.
  • Every city is independent. Trips do not cross cities, so shard by city and fail by city.

Architecture

  1. The driver app streams its position every 4 seconds over a persistent connection.
  2. The ingest tier appends each ping to a Kafka topic partitioned by city.
  3. Index builders consume the topic and keep an in-memory map from H3 cell to the drivers inside it. An entry expires after 30 seconds without a ping.
  4. A rider requests a ride. The trip service creates a trip in state REQUESTED under an idempotency key.
  5. It asks the city's matching service for a driver.
  6. Matching reads the rider's cell, then the rings of cells around it, until it has enough candidates.
  7. Candidates are ranked by road travel time from the ETA service.
  8. Matching reserves the best driver with a compare-and-set and sends the offer down that driver's connection. Accepting moves the trip to MATCHED.

Data model and API

stream  location(driver_id, lat, lng, heading, ts)      every 4 s
POST /rides {pickup, dropoff, idempotency_key} -> trip_id, state
POST /offers/{id}/accept | /decline                     (driver)
GET  /trips/{id}        + push of state and driver position

geo (memory)  cell_id -> {driver_id}
              driver_id -> cell, position, ts            TTL 30 s
drivers       driver_id -> state, trip_id, version       CAS on version
trips         trip_id -> rider, driver, state, fare      shard: city
states  REQUESTED > MATCHED > ARRIVING > IN_TRIP > COMPLETED | CANCELLED

The hard part: one driver, two requests, one winner

The reservation is one conditional write: set state=OFFERED, trip=1, version=13 where driver=D7 and version=12. Any store with compare-and-set will do: a Redis script, a DynamoDB conditional update, or a version column in SQL.

The offer carries a 15-second TTL. If the driver declines, lets it time out, or the matching process dies, the driver returns to AVAILABLE and the trip goes to the next candidate. Nothing needs cleaning up by hand.

The geo index is allowed to be slightly wrong because it only proposes candidates. The driver record is the authority on whether a driver is free.

When supply is tight, collect requests for 2 to 3 seconds and solve the batch as an assignment problem that minimises total pickup time. It beats greedy first-come matching, and the same compare-and-set still guards each assignment.

Trade-offs

An in-memory cell index fed by a stream over a spatial database

At 1.25M writes a second, on data that is worthless after 30 seconds, durability is wasted work. After a crash the index rebuilds from the last 30 seconds of the topic.

H3 hexagons over geohash squares

Every neighbour of a hexagon is the same distance away, so widening the search by one ring means the same thing in every direction. Geohash also works, with awkward edges where adjacent cells share no prefix.

Rank by road ETA over straight-line distance

The nearest driver across a river or on the far side of a motorway is a slow pickup.

Shard by city over one global cluster

Trips never cross cities. A bad deploy or an overloaded index takes out one city, and capacity can follow local peaks.

Failure modes

  • An index node dies. A replica takes over, or a fresh node replays the last 30 seconds of pings. Match quality dips for a few seconds.
  • Matching dies after reserving a driver. The reservation's TTL frees the driver. A sweeper retries trips stuck in REQUESTED.
  • A driver's phone loses signal. The index entry expires, so no new offers go out. During a trip the app buffers GPS points and uploads them when signal returns.
  • The rider's app retries the request. The idempotency key returns the existing trip.

Staff additions

Cut from version one
Pooling, scheduled rides, surge pricing, batch matching. Version one is one city, greedy matching, flat fares.
Monitor and page on
Time to match at p95, offer acceptance rate, age of the newest ping per city, ETA error against actual pickup time, and the count of drivers holding two active trips, which must stay at zero.

UPI-style payment switch

bank-to-bank transfers in seconds

The switch holds no money. It runs a debit at one bank and a credit at another, in that order, inside a deadline of seconds, across companies that fail independently. Everything interesting is in what happens when a reply does not come back: the switch must find out what happened and never guess.

Requirements and scale

  • About 700 million payments a day. That is 8,000 a second on average and several times that on salary days and festivals.
  • Each payment touches four outside parties: two apps and two banks. Any of them can be slow.
  • The customer gets a final answer within about 15 seconds. Every hop has its own timeout inside that budget.
  • Money is never created or destroyed. Every debit ends as exactly one credit or one reversal.
  • The switch keeps an exact record of who owes whom, and banks settle the net a few times a day.

Architecture

  1. The payer enters the amount and UPI PIN. The PIN is encrypted on the device with a key that only the payer's bank can use.
  2. The payer's PSP sends the payment request to the switch with a unique txn_id.
  3. The switch asks the payee's PSP to resolve the payee's address to a bank account.
  4. The switch writes the transaction, then sends the debit to the payer's bank, which checks the PIN and the balance.
  5. On a confirmed debit, it sends the credit to the payee's bank.
  6. Both apps get the final result.
  7. Every leg is appended to a ledger. A few times a day the net position of each bank is computed and settled between the banks' accounts at the central bank.

Data model and API

ReqPay    (txn_id, payer_vpa, payee_vpa, amount, encrypted PIN)
RespPay   (txn_id, result, response code)
ReqChkTxn (txn_id) -> last known result          safe to repeat
every message is signed, sent over mutual TLS, idempotent on txn_id

txns   txn_id -> state, payer, payee, amount, deadline
legs   (txn_id, leg) -> bank, DEBIT | CREDIT | REVERSAL, result, bank ref
net    (cycle, bank) -> credits - debits  -> settlement file

states  INIT > DEBITED > CREDIT_SENT > SUCCESS
                       > REVERSAL_SENT > REVERSED
        INIT > FAILED                            (nothing was debited)

The hard part: the debit succeeded and the credit timed out

A timeout carries no information. The credit may have been applied and the reply lost. Reversing the debit on a timeout alone can pay the payee and refund the payer, which creates money. Blindly sending the credit again can pay twice.

So every message carries the same txn_id, and every bank treats a repeat of that id as a question about the first attempt. The switch keeps asking what happened to T1 until the answer is definite, then moves to SUCCESS or starts a reversal. The reversal is itself idempotent on the same id.

The state is written before each outbound call. If the switch crashes, the sweeper finds every transaction that has sat in a non-final state past its deadline and resumes it from the log.

If the payee bank stays silent until the settlement cycle closes, the payment is settled as deemed successful and resolved in reconciliation: each bank's end-of-cycle file is compared with the switch's ledger, and every mismatch becomes an automatic adjustment or a dispute.

Trade-offs

A saga driven by a durable state machine over a distributed transaction across banks

Two-phase commit needs every bank to hold locks until a coordinator decides, and the banks are separate companies with separate uptime. A saga holds no locks. Debit, then credit, with reversal as the compensating step.

Debit first, then credit over credit first

If the second leg fails after a debit, the customer is owed a refund that the system controls. If it failed after a credit, the money would have to be taken back from someone who may already have spent it.

Deferred net settlement between banks over moving real money for each payment

Customers see a result in seconds while banks settle the net of millions of payments a few times a day. The cost is exposure between banks until the cycle settles, which is why cycles are short and settlement is guaranteed.

A connection pool and circuit breaker per bank over one shared worker pool

One slow bank would otherwise hold every thread and stop payments between healthy banks. With bulkheads, a failing bank is declined fast and everyone else is unaffected.

Failure modes

  • The payer's bank is slow. Its breaker opens and new payments from that bank are declined at once with a clear code. Nothing was debited, so the decline is final.
  • A switch node dies mid-transaction. State was written before the call went out. The sweeper resumes with a status check.
  • A PSP retries the same payment. The txn_id is the idempotency key. The switch returns the stored result.
  • A data centre is lost. The transaction store is replicated synchronously to a second site. In-flight transactions resume there as status checks.

Staff additions

Cut from version one
Collect requests, mandates and autopay, credit on UPI, cross-border. Version one is a push payment between two banks.
Monitor and page on
Success rate per bank, split into technical declines and business declines such as wrong PIN. Transactions in a non-final state past their deadline. Reversal backlog and its oldest entry. Settlement mismatches per cycle. Page on a bank's technical decline rate and on any transaction still unresolved when its cycle closes.

News feed

like Instagram or LinkedIn

A feed is read far more often than it is written, so do the work when someone posts: push the post id into each follower's cached feed. That breaks for accounts with millions of followers, so those are merged in at read time instead. The answer is the hybrid, plus a ranking step over the merged candidates.

Requirements and scale

  • 500M daily users opening the feed about 10 times a day. That is 60,000 feed reads a second on average and 200,000 at peak.
  • 100M posts a day, about 1,200 a second. With a few hundred followers each, that becomes roughly 300,000 feed inserts a second.
  • A feed loads in under 200 ms at p99. A new post reaches followers within about 5 seconds.
  • A few accounts have tens of millions of followers. One post from them must not turn into 50M writes.
  • Eventual consistency is fine everywhere except one place: authors must see their own post immediately.

Architecture

  1. The author publishes a post.
  2. The post service stores it and returns. Posting never waits for followers.
  3. A new-post event is emitted from the store.
  4. Fan-out workers consume the event.
  5. They look up the author's followers. If the author is over the follower threshold, they stop here.
  6. Otherwise they push the post id onto each active follower's feed list, which is capped at about 800 entries.
  7. A reader opens the app.
  8. The feed service reads that user's list of ids from the cache.
  9. It adds recent posts from any huge accounts the reader follows, ranks the merged candidates, and fetches the bodies of the top 20 from the post store.

Data model and API

POST /posts {text, media_ids}          -> post_id
GET  /feed?cursor=...&limit=20         -> posts[], next_cursor
POST /follow {target}

posts    post_id -> author, body, media, ts       shard: post_id
follows  (follower, followee) + reverse index (followee, follower)
feed:{user}      list of post_id, newest first, cap 800     Redis
recent:{author}  last 100 post_ids, kept for pull authors

The hard part: who pays for a post, the writer or the reader

Pure push fails on stars: one post becomes 50M writes, the queue backs up, and everyone's feeds go stale. Pure pull fails on readers: every feed open queries hundreds of authors. The hybrid keeps both costs bounded.

Feeds store post ids and a score, never bodies. An edit or delete then touches one row, and the hydrate step drops anything deleted, blocked or private at read time.

Skip fan-out to users who have not opened the app in 30 days. When they return, rebuild their feed once by pulling from the accounts they follow. This removes most of the write volume.

Ranking runs over the merged candidates, usually a few hundred: a cheap model scores each one from features such as author affinity and recency, and the top results are hydrated. Paginate with a cursor on score and id, because offsets shift as new posts arrive.

Trade-offs

Push for most authors, pull for the largest over pure push or pure pull

Each pure strategy has one case where its cost is unbounded. The hybrid adds a threshold and a merge step, and both costs stay small.

Fan-out through a queue over fan-out inside the post request

Posting returns in milliseconds and followers see the post a second or two later. The author's own feed merges their recent posts at read time so they never notice the delay.

Ids in the feed cache over full posts in the feed cache

Ids are 8 bytes and never go stale. Bodies live in one place with one cache.

Cursor pagination over page numbers

New items arrive while the reader scrolls. An offset would repeat or skip posts.

Failure modes

  • Fan-out falls behind. Queue age grows and feeds go stale. Workers scale on queue age, and the feed service can fall back to pulling for the accounts a reader interacts with most.
  • A feed cache node is lost. Affected feeds are rebuilt on demand by pulling recent posts from followed accounts, then cached again.
  • A deleted post is still listed in feeds. Hydration drops it. The feed service fetches a few extra candidates so the page is still full.
  • A star's list becomes a hot key. recent:{author} is replicated and cached in the feed service for a few seconds.

Staff additions

Cut from version one
Ranking, ads, stories, recommendations from accounts you do not follow. Version one is a chronological feed with push fan-out and a follower cap.
Migration path
From pull-only: start writing feed lists for a small cohort while still serving them by pull, compare the two results offline, then switch reads cohort by cohort.
Monitor and page on
Feed latency at p99, fan-out lag from post to presence in a follower's list, feed cache hit ratio, share of feed opens that return fewer than 20 items. Page on fan-out lag and on the empty-feed rate.

Flash sale

Flipkart's Big Billion Days

Ten million people press Buy in the same second for ten thousand units. Only ten thousand requests can ever succeed, so the job is to say no to everyone else as early and as cheaply as possible, never sell unit 10,001, and keep the rest of the site working. Shed load in layers, and make the stock decrement one atomic operation.

Requirements and scale

  • 10M shoppers waiting on one product page, 10,000 units, a start time known in advance.
  • Over 1M requests a second in the first seconds. The order database handles a few thousand writes a second.
  • Zero oversell. Selling a unit you do not have is worse than selling out a second later.
  • Fair enough that bots and fast connections do not take everything. One unit per customer.
  • Search, browse and normal checkout elsewhere on the site are unaffected.

Architecture

  1. The page, images and countdown come from the CDN. At noon everyone presses Buy, and the request goes to an edge gateway that drops bots and repeat clicks.
  2. Survivors are placed in a waiting room and shown their position.
  3. The waiting room hands out tokens at a fixed rate that the reserve API can absorb.
  4. With a token, the reserve API runs one atomic operation on the stock counter: if any are left and this user has not bought, take one.
  5. A successful reservation goes onto the order queue, and the shopper sees "reserved".
  6. Order workers drain the queue at the database's pace and create the order, re-checking stock with a conditional update.
  7. The shopper has 10 minutes to pay. An unpaid reservation expires and its unit goes back into the counter.

Data model and API

GET  /sale/{sku}                  static, from CDN, carries start time
POST /sale/{sku}/enter            -> ticket                  (at T0)
GET  /sale/{sku}/ticket/{id}      -> position | token        (polled)
POST /sale/{sku}/reserve {token, idempotency_key} -> hold_id, expires
POST /orders/{hold_id}/pay

stock:{sku}    integer in Redis, loaded once before the sale
buyers:{sku}   set of user ids                   one unit per user
holds     hold_id -> user, sku, expires_at, state
orders    order_id -> user, sku, hold_id UNIQUE, state
inventory sku -> left      update ... where left > 0    final guard

The hard part: what each layer throws away

The counter operation is a short script that Redis runs single-threaded: if stock > 0 and the user is not in buyers, decrement, add the user, return a hold. No two requests can interleave inside it, and one key handles around 100,000 of these a second.

The counter is fast but it is a cache of the truth. The order worker repeats the check in the database with update inventory set left = left - 1 where sku = ? and left > 0. If a Redis failover loses a few decrements, this second guard is what prevents an oversell.

When the counter reaches zero, a sold-out flag is published and cached at the edge. From then on the gateway answers without calling anything behind it.

The waiting room assigns a random position to everyone who arrives in the first few seconds. Strict arrival order would reward bots and people who live near the data centre.

Trade-offs

Reject early and cheaply over scaling the order path to meet the peak

Only 10,000 requests can succeed. Building a checkout that takes 1M writes a second for ten seconds a year is money spent to say "sold out" more expensively.

An in-memory counter with the database as final guard over row locks in the database

A locked inventory row serialises every buyer through one disk write and collapses under contention. The counter decides in microseconds, and the database only confirms decisions it can keep up with.

Reserve now, create the order asynchronously over writing the order inside the request

The shopper gets an answer in milliseconds and the queue absorbs the burst. The cost is a short "confirming your order" state and the need for idempotent workers.

A dedicated pool for the sale over sharing the normal checkout fleet

A sale that overloads its own pool is a bad sale. One that takes down the whole site is an incident.

Failure modes

  • The counter node fails over and loses recent decrements. A few extra holds are issued. The database guard rejects them at order creation, and those shoppers are told the item sold out.
  • The order queue backs up. Shoppers stay on "confirming". The payment clock starts when the order is created, so nobody loses time they could not use.
  • The payment provider is slow. A hold with a payment in progress is not released on timeout. It is resolved from the provider's final status.
  • Clients retry in a storm. The wait page polls a CDN-cached object with jittered backoff. Reserve calls are idempotent on the key.

Multi-item carts, loyalty tiers in the queue, restock waves. Version one is one product, one unit per user.
Migration path
From normal checkout: put the waiting room in front of the existing flow first. That alone caps the load. Add the in-memory counter when the database guard becomes the bottleneck.

Units sold against units available, which must never exceed 100%. Reserve API errors, order queue age, holds expiring unpaid, and the p99 of ordinary checkout during the sale. Page on any oversell and on ordinary checkout degrading.

Sheet 08 of 20System design

Distributed file storage

like Google Drive

Keep the bytes and the facts about them in different systems. Files are cut into blocks named by their hash and stored once, immutably. A file version is only a list of hashes held in a transactional metadata store. Devices stay in sync by reading an ordered journal of changes from wherever they last stopped.

Requirements and scale

  • 1 billion accounts, hundreds of millions of devices syncing each day, total storage in exabytes.
  • Files range from a few bytes to tens of gigabytes. Most files are small and most bytes are in large ones.
  • Eleven nines of durability. Losing a customer's file is the one failure that cannot be explained away.
  • An edit on one device appears on the others within seconds when they are online.
  • Devices go offline for days and reconnect on poor networks. Uploads must resume.

Architecture

  1. The sync client notices a changed file, splits it into 4 MB blocks, hashes each one, and uploads only the blocks the server does not already have.
  2. Blocks are stored under their hash. Storing the same block twice is a no-op.
  3. The client commits a new version: the ordered list of block hashes plus the version it started from.
  4. The metadata service applies the commit in one transaction if the file's head is still that base version.
  5. The same transaction appends an entry to the owner's change journal.
  6. The journal entry wakes the notify service.
  7. Other devices holding a connection are told to pull.
  8. Device B asks for changes after its cursor, receives the new block list, and downloads the blocks it is missing.

Data model and API

POST /blocks/missing {hashes[]}      -> hashes the server lacks
PUT  /blocks/{sha256}                4 MB, immutable, idempotent
POST /files/{id}/commit {base_version, blocks[], size, mtime}
                                     -> version | 409 conflict
GET  /changes?cursor=8841            -> entries[], next_cursor
GET  /notify                         long poll or WebSocket: "pull now"

files     (owner, file_id) -> parent, name, head_version, deleted
versions  (file_id, version) -> blocks[], size, mtime, device
journal   (owner, seq) -> file_id, version, op      seq only increases
blocks    sha256 -> location, refcount              bytes: object store

The hard part: editing 4 MB of a 1 GB file

Naming blocks by their hash gives three things at once. Unchanged blocks are never re-sent, an interrupted upload resumes by asking the same question again, and identical content is stored once across versions.

Blocks are immutable and uploaded before the commit, so the commit itself is small: a compare-and-set on head_version plus a journal append, in one transaction on one shard. Either the whole new version exists or none of it does.

Two devices that both edit version 1 offline will both try to commit against base v1. The first wins. The second gets a conflict and saves its work as a separate "conflicted copy" file. The system never picks a winner by silently discarding someone's edit.

Uploading before committing leaves orphan blocks when a client disappears mid-way. A garbage collector removes blocks that no version references after a grace period.

Trade-offs

Separate stores for metadata and bytes over one system for both

Metadata needs transactions over small rows. Bytes need cheap, durable bulk storage. Splitting them lets clients send bytes straight to object storage.

Fixed 4 MB blocks named by hash over whole-file uploads

Edits, resumes and deduplication all fall out of one mechanism. Content-defined chunking finds more duplicates when bytes are inserted mid-file, at the cost of client CPU, and is a reasonable later upgrade.

A pull-based journal with push hints over pushing full changes to devices

Devices are offline for days. With a cursor into an ordered journal, catching up and staying current are the same operation, and a lost notification costs only a delay.

Transactional metadata sharded by owner over an eventually consistent store

Renames and moves in a file tree need transactions, and almost all of them touch one owner's tree. Shared folders are the hard case. Give each shared folder its own namespace id and shard on that.

Failure modes

  • An upload is interrupted. The client asks again which hashes are missing and continues from there.
  • A disk or a rack is lost. Blocks are erasure coded across failure domains, for example 6 data and 3 parity fragments. A background scrubber re-reads blocks, checks them against their hash and repairs from parity.
  • A metadata shard is unavailable. Those owners cannot commit. Clients queue changes locally and keep working on files they already have.
  • A notification is missed. The device polls the journal on a timer anyway. The notification only shortens the wait.

Staff additions

Cut from version one
Sharing, team folders, content-defined chunking, cross-user deduplication. Version one is one user syncing several devices.
Migration path
From whole-file storage: keep old files as they are and chunk each one the next time it is written. Backfill cold files in the background by size, largest first.
Monitor and page on
Commit latency and error rate, sync lag measured as journal head minus device cursor, scrub failures, growth of unreferenced blocks, open notify connections. Page on any scrub that cannot repair and on commit errors.

Typeahead search

millions of queries per second

A suggestion has to come back before the next keystroke, millions of times a second. The only way to do that is to do no work per request: compute the top ten completions for every prefix ahead of time, hold that map in memory, and let most requests be answered by a cache at the edge. Freshness comes from rebuilding the map, never from the request path.

Requirements and scale

  • 10 billion searches a day, with about 6 suggestion requests for each after debouncing. That is 700,000 requests a second on average and 2M at peak.
  • Under 100 ms from keystroke to dropdown, which leaves the server about 20 ms at p99.
  • Hundreds of millions of distinct queries, a few billion prefixes worth indexing.
  • Suggestions reflect popularity within the hour, and breaking events within minutes.
  • If suggestions fail, search itself must keep working.

Architecture

  1. The browser waits about 100 ms after the last keystroke, then requests suggestions for the prefix. Answers are the same for every user, so the edge can cache them.
  2. On a cache miss a suggest node looks the prefix up in an in-memory map and returns ten strings. There is no database or downstream call.
  3. When the user actually runs a search, the query is logged.
  4. A stream job aggregates queries into counts with time decay.
  5. It filters out anything rare, private or offensive and passes the surviving queries on.
  6. The builder computes the top ten for every prefix and writes a new immutable snapshot.
  7. Suggest nodes load the snapshot beside the old one and switch over atomically. Rolling back is loading the previous file.

Data model and API

GET /suggest?q=sys&lang=en&n=10      -> ["system design", ...]
    Cache-Control: public, max-age=300       same for every user

index  (immutable, in RAM)   prefix -> [(query_id, score) x 10]
queries                      query_id -> text, flags
query_counts (build input)   (query, hour) -> count
delta index  (last 15 min)   prefix -> [(query_id, score) x 10]
shard = first two characters of the prefix, 3 replicas per shard

The hard part: where the work happens

A 20-character query appears in 20 prefix lists, so the index is several times larger than the list of queries. Cap prefix length at about 20 characters and drop prefixes whose best completion is too rare to show.

The build is a batch job: emit (prefix, query, score) for every prefix of every query, keep the top ten per prefix, write a sorted file. Scores decay with age so last year's event does not outrank this week's.

Hourly builds miss breaking news. A second, tiny index built from the last 15 minutes of the stream is merged with the main one at serving time.

Keep the answer identical for every user so it stays cacheable. One, two and three-letter prefixes are most of the traffic and have very few distinct values. The device merges in the user's own recent searches.

Trade-offs

Top ten stored per prefix over walking a trie on each request

Request cost becomes constant and tiny. The index grows, which is a storage cost paid once per build.

Immutable snapshots swapped atomically over updating the index in place

The read path takes no locks, and a bad build is undone by pointing at the previous file. Freshness is limited to the build interval, which the delta index covers.

One shared answer per prefix over personalised suggestions from the server

A shared answer can sit in a CDN. Personal history is small and is merged on the device.

Shard by prefix range over hashing whole queries

Every list for prefixes starting with "sy" lives on one shard, so a request touches one node.

Failure modes

  • A suggest node dies. Each node holds its shard's whole index in memory and calls nothing else. The load balancer drops it and the replicas absorb the traffic.
  • A build produces junk. The builder compares size and a sample of top prefixes against the previous snapshot and refuses to publish a large unexplained change. Canary nodes load first.
  • The suggest tier is down. The search box fails open. The client gives up after 200 ms and the user types the full query.
  • Everyone types the same thing at once. That is the best case for the edge cache. The delta index picks up the new query within minutes.

Staff additions

Cut from version one
Personalisation, typo tolerance, the delta index. Version one is an hourly batch build and an in-memory map behind a CDN.
Migration path
From querying the search index with a prefix filter: build the snapshot offline, serve it in shadow, compare suggestion click-through, then switch.
Monitor and page on
Server latency at p99, edge hit ratio, index age, the share of searches that came from a clicked suggestion, build validation failures. Page on index age over two build intervals and on p99.

Live cricket scores

50 million concurrent users

Almost nothing is written and almost everyone is reading: one event per ball, fifty million phones that all want it within two seconds, and every one of them gets identical bytes. Serve the full scorecard from a CDN and push small numbered updates down long-lived connections through a fan-out tree. Sequence numbers let any phone repair itself.

Requirements and scale

  • 50M phones connected during a big final, nearly all on the same one or two matches.
  • Writes are tiny: one event per ball, a few a minute per match.
  • A new ball reaches every phone within 2 seconds of the scorer entering it.
  • Spikes are sudden and predictable. The toss, a wicket or the last over can bring 10M people in within a minute.
  • Nothing is personalised, so everything can be cached and shared.

Architecture

  1. The scorer records a ball. The feed is idempotent on the ball id, and a correction is a new event.
  2. Ingest validates it, assigns the next sequence number for the match and appends it to the match log.
  3. The event is published on the match's topic.
  4. Relays subscribed to the topic receive the delta.
  5. Each relay forwards it to its gateways. The tree keeps any one node's fan-out small.
  6. Each gateway writes the same serialised frame to every socket subscribed to that match.
  7. In parallel the snapshot service rebuilds state.json and puts it on the CDN with a one-second lifetime. A phone opening the app reads that first, then subscribes from the snapshot's sequence number.

Data model and API

GET  cdn/matches/{id}/state.json    full scorecard + seq    max-age 1 s
GET  /matches/{id}/stream           SSE, header Last-Event-ID: 1041
     event: {seq, over, ball, runs, extras, wicket, score}
POST /internal/matches/{id}/events  scorer feed, idempotent on ball id

events   (match_id, seq) -> ball payload    append only, source of truth
state    match_id -> scorecard, seq         rebuilt from events
gateway  ring buffer of the last 100 events per match, in memory
client   apply an event if seq == mine + 1, otherwise refetch state.json

The hard part: one message to fifty million sockets

Push is best-effort and unacknowledged. Every event carries seq, and a phone applies only the event that follows the one it has. If it sees a gap it fetches the snapshot from the CDN and carries on. Tracking delivery for 50M sockets would cost more than the rest of the system.

Gateways keep the last hundred events per match in memory. A phone that reconnects with Last-Event-ID gets the events it missed without anything upstream being asked.

Capacity is provisioned before the match from the fixture list. Ten million arrivals in a minute is faster than any autoscaler, and the first thing each arrival does is read a cached file, so the origin never sees the crowd.

If the push tier is struggling, a flag in the snapshot tells phones to stop streaming and poll state.json every few seconds. The CDN can carry that, and scores are a few seconds late instead of missing.

Trade-offs

Push over long-lived connections over every phone polling

A ball arrives about twice a minute. Polling every 2 seconds would be 25M requests a second, nearly all answered "no change". Push sends frames only when something happened.

Snapshot from the CDN, deltas on the stream over full state on the stream

Opening the app, reconnecting and recovering from a gap all become one cached GET, and the stream stays tiny.

Server-sent events over WebSockets

Data flows one way. SSE is plain HTTP, reconnects by itself and carries the last event id for free.

Capacity booked before the match over autoscaling during it

The schedule is known weeks ahead and the ramp takes under a minute. New instances would arrive after the wicket.

Failure modes

  • A gateway dies. A million phones reconnect to other gateways with jittered backoff and resume from their last event id.
  • A relay misses messages. It sees the gap in sequence numbers and reads the missing events from the match store.
  • The scorer's link drops. A second scorer feed takes over. Ingest drops duplicate ball ids, so both feeds can run at once.
  • The snapshot expires on thousands of edges together. Edges serve the stale copy while one request per region revalidates through an origin shield.

Staff additions

Cut from version one
The whole push tier. A CDN snapshot polled every 2 seconds meets the requirement for the first few million users and is a day's work. Add push when request cost or latency demands it.
Monitor and page on
Event age at the phone, sampled, from scorer timestamp to render. Sockets per gateway, reconnect rate, CDN hit ratio, sequence gaps seen by relays. Page on event age and on a reconnect storm.

Exactly-once event processing

across microservices

Exactly-once delivery does not exist: a network can always deliver a message and lose the acknowledgement. What you can build is exactly-once effect. Deliver at least once, make the event part of the producer's database commit, and make the consumer record each event id in the same transaction as the work it does.

Requirements and scale

  • Dozens of services exchanging tens of thousands of events a second. Each event changes money, stock or something a customer can see.
  • No event is lost. No event takes effect twice.
  • Any process can crash at any line, and any message can be delivered more than once.
  • Events about the same entity are handled in order.
  • A delay of a second or two end to end is fine. Making the user's request wait on downstream services is not.

Architecture

  1. The order service writes the order and an outbox row describing the event in one database transaction. Either both exist or neither does.
  2. A relay reads new outbox rows in commit order.
  3. It publishes each one to the broker, keyed by the entity id so that events for one order stay in one partition, then marks the row as sent. If it crashes between those two steps it publishes again.
  4. The broker delivers the event to the payment worker, possibly more than once.
  5. The worker opens a transaction, inserts the event id into its inbox table, does its work, and commits.
  6. Only after the commit does it acknowledge. An event that fails five times is moved to a dead-letter topic so the partition keeps moving.

The three transactions

-- producer: one transaction
insert into orders (...);
insert into outbox (event_id, aggregate_id, type, payload);

-- relay
select * from outbox where published_at is null order by id limit 500;
publish(key = aggregate_id, header event_id); mark published

-- consumer: one transaction, then ack
insert into inbox (consumer, event_id);    -- unique; on conflict: skip
update payments ...;
insert into outbox (...);                  -- its own events
commit;

The hard part: the crash between the work and the ack

There are three places an event can be lost or doubled. Between the producer's database and the broker, which the outbox closes. Inside the broker, which redelivers by design. Between the consumer's work and its ack, which the inbox closes.

The event id is assigned once, by the producer, when the outbox row is written. It never changes across retries. Everything downstream dedupes on it.

When the consumer's effect is a call to another company, such as a card network, it cannot sit inside a database transaction. Pass the event id as that API's idempotency key and let the far side dedupe.

A broker's exactly-once mode covers reading from one topic and writing to another within the broker. It cannot cover a row in your database, which is why the inbox is still needed.

Trade-offs

A transactional outbox over publishing from application code after the commit

A crash between commit and publish loses the event for good. Publishing before the commit announces things that never happened. The outbox makes the event part of the same commit.

An inbox table in the consumer's database over relying on the broker's exactly-once mode

Dedupe has to be atomic with the effect, and the effect lives in the consumer's database.

At-least-once delivery over at-most-once

A duplicate can be detected and dropped. A lost event cannot be detected at all.

Change data capture on the outbox over a polling relay

CDC reads the database log, adds no query load and keeps commit order. A poller is simpler to run and is enough up to a few thousand events a second.

Failure modes

  • The relay publishes, then crashes before marking the row. It publishes the row again on restart. Consumers drop the duplicate.
  • One event fails every time. After five attempts it goes to the dead-letter topic with the error attached, and someone is alerted. Later events for the same entity are held until it is resolved, so order is kept.
  • The broker is down. Business transactions still commit and outbox rows pile up. The relay drains them when the broker returns.
  • The inbox table grows without end. Partition it by day and drop partitions older than the broker's longest possible redelivery window.

Staff additions

Cut from version one
CDC, a dead-letter replay tool, a schema registry. Version one is a polling relay and an inbox table.
Migration path
From publishing directly: add the inbox to consumers first, because duplicates begin the moment a relay exists. Then write outbox rows beside the existing publish, switch the relay on, and remove the direct publish.
Monitor and page on
Age of the oldest unpublished outbox row, consumer lag, dead-letter depth, end-to-end event age. Watch the inbox duplicate rate: a spike means something upstream is redelivering in bulk.

Loan approval

credit checks across multiple bureaus

This is a workflow problem, and throughput hardly matters. One application runs for seconds or days, calls outside companies that are slow, expensive and sometimes down, may wait for a person, and must be explainable years later. Use a durable workflow engine, pull from bureaus in parallel against a deadline, and keep the decision a pure function of recorded inputs.

Requirements and scale

  • 1M applications a day at a large lender. That is about 12 a second and 100 at peak.
  • 80% of applicants get a decision within 10 seconds. The rest go to a person and may take days.
  • Three or four credit bureaus, each a third party with its own latency, outages and fee per pull.
  • A hard credit pull lowers the applicant's score and costs money. It happens at most once per application.
  • Every decision can be explained and reproduced years later.

Architecture

  1. The applicant submits. The API dedupes on an idempotency key and on applicant plus product within 24 hours.
  2. A workflow instance starts, pinned to the current policy version.
  3. Cheap checks run first: identity, fraud signals, internal blacklists, affordability. Failing here ends the application before any bureau is charged.
  4. The bureau gateway pulls reports in parallel under one deadline.
  5. The decision engine takes the application, the reports and the policy version and returns approve, reject or refer, with reasons.
  6. Grey-zone cases go to a review queue. The workflow sleeps until a person acts.
  7. An underwriter decides, and the workflow resumes. Every input, output and actor is in the audit log.

Data model and API

POST /applications {applicant, amount, tenure, idempotency_key}
     -> application_id, status
GET  /applications/{id}            -> status, decision, reasons
POST /applications/{id}/review {decision, notes}      (underwriter)

applications  id -> applicant, amount, status, policy_version
steps         (application_id, step) -> state, attempts, result ref
bureau_pulls  (application_id, bureau) UNIQUE -> request id,
              report ref, pulled_at, cost        one hard pull, ever
decisions     application_id -> outcome, reasons[], inputs hash
audit         append only: who or what did what, with which data

status  SUBMITTED > VERIFYING > PULLING > DECIDING
        > APPROVED | REJECTED | REFERRED > APPROVED | REJECTED

The hard part: three bureaus, one deadline

Each pull is a workflow activity with its own timeout and retry policy, and each carries an idempotency key of application id plus bureau. If a response is lost, the retry fetches the result of the first request. The unique key on bureau_pulls is the last line of defence against a second inquiry on someone's credit file.

A missing report is data. The rules can say "two of three is enough", or "one is enough if the score is above 780", or "refer if the missing bureau is the only one with history for this applicant".

Reports are cached for as long as regulation allows, commonly 30 days. Someone who reapplies next week is decided on the report already paid for.

The decision engine has no side effects. Given the same application, reports and policy version it returns the same outcome and the same reasons. That is what makes a decision reproducible for an auditor and safe to re-run after a crash.

Trade-offs

A durable workflow engine over chained queues or a job that sweeps a status column

The process has timers, retries, parallel branches and a step that waits days for a person. Temporal or Step Functions persist each step and resume after a crash. A hand-built status machine ends up growing the same features with more bugs.

Parallel pulls with a deadline and a quorum over calling bureaus one after another

Latency becomes the slowest bureau you chose to wait for, and one bureau being down does not stop lending.

Cheap checks first, the hard pull last over pulling credit at the start

A hard inquiry costs money and marks the applicant's file. Spend it only on people who have passed identity, fraud and affordability.

A versioned decision function over rules spread across services

Customers and regulators ask why. With inputs, policy version and reasons stored together, any decision can be replayed exactly.

Failure modes

  • A bureau is down. Its branch retries inside the deadline, then the workflow continues on quorum or refers the application.
  • The bureau charged for a pull and the response was lost. The gateway asks again with the same request id and gets the same report. No second pull is made.
  • A workflow worker crashes mid-application. The engine replays the recorded history on another worker. Completed steps are not run again.
  • Policy changes while applications are in flight. Each application finishes on the version it started with, so its outcome can still be explained.

Staff additions

Cut from version one
Co-applicants, document OCR, pre-approved offers, more than one bureau. Version one is one product, one bureau, and an automatic decision or a referral.
Migration path
From a synchronous monolith: put the gateway in front of the existing bureau call first, which gives idempotency and caching at once. Then move orchestration into the workflow engine one step at a time.
Monitor and page on
Time to decision at p50 and p95, automatic decision rate, success rate and latency per bureau, bureau cost per approved loan, age of the review queue, workflows stuck in one step. Page on stuck workflows and on a bureau's success rate.

Sheet 13 of 20System design

Distributed unique ID generator

like Twitter Snowflake

Pack a timestamp, a worker number and a counter into 64 bits, and a process can mint unique, time-sorted ids from memory with no network call. Only two things can break it: two processes holding the same worker number, and a clock that moves backwards. The design is mostly about those two.

Requirements and scale

  • Ids are 64-bit integers, unique across every data centre, for decades.
  • Roughly ordered by creation time, so they work as primary keys and as sort keys.
  • Tens of thousands of ids a second per process and millions a second across the fleet.
  • Generating an id takes about a microsecond and makes no network call.
  • No single point of failure. A registry outage must not stop generators that are already running.

Architecture

  1. At start-up each process leases a worker number from the registry. The lease has a TTL and is renewed by heartbeat.
  2. A caller asks for an id. This is a function call in the same process.
  3. The generator reads the local clock, picks the sequence number for this millisecond and packs the three fields into 64 bits.
  4. If a process cannot renew its lease, it stops issuing ids before the lease runs out. Another process can then take the worker number with no overlap.

Bit layout and API

bit 63                                                       bit 0
 | 0 | 41 bits: ms since custom epoch | 10: worker | 12: sequence |

next_id() -> int64                  in process, about 1 microsecond
id = (now_ms - EPOCH) << 22 | worker_id << 12 | sequence

41 bits of ms  = 69 years          10 bits = 1,024 workers
12 bits        = 4,096 ids per ms per worker = 4M a second each

registry  /workers/{0..1023} -> owner, lease expiry      etcd or ZK
local     last_ms, sequence                              in memory
decode    ts = (id >> 22) + EPOCH     worker = (id >> 12) & 1023

The hard part: what next_id() does when time misbehaves

The id is unique because the triple of timestamp, worker and sequence is never reused. If the clock steps back 50 ms and the generator carries on, it will produce timestamps it has already used, with sequence numbers it has already used. That is a duplicate primary key.

Clocks do step back: an NTP correction, a virtual machine paused and resumed, a leap second. For a small step, sleep until the clock catches up. For a large one, fail the call and take the process out of rotation. Callers can retry on another instance.

A restart forgets last_ms. Persist a high-water mark every few seconds, a little ahead of the clock, and on start-up wait until the clock is past it.

Worker numbers are the only coordination. A process that pauses for longer than its lease, during a long garbage collection for example, must check the lease against a monotonic clock before issuing again, because someone else may now hold its number.

Trade-offs

A library in every process over a central id service

No network hop and nothing to be down. The cost is that each process needs a unique worker number.

64 bits with a worker number over 128-bit UUIDv7

UUIDv7 is also time-ordered and needs no worker numbers, so where 128 bits are acceptable it is less to operate. Snowflake earns its place when ids must fit a 64-bit integer column.

Time in the high bits over random ids

New rows land at the end of the index, which keeps inserts fast, and a time range becomes an id range. The cost is that an id reveals when it was made and hints at volume.

Refuse to issue when the clock is wrong over issuing anyway

A short pause is an inconvenience. A duplicate key is corruption.

Failure modes

  • The registry is down. Running processes keep their leases until the TTL, which is set in minutes. New processes wait to start.
  • One process needs more than 4,096 ids in a millisecond. It waits for the next millisecond. If that happens often, run more processes.
  • A browser receives the id as a number. JavaScript numbers hold 53 bits, so the last digits change silently. Send ids to clients as strings.
  • Clocks on two hosts disagree by a second. Ids are still unique. Their order across hosts is only as good as clock sync, so never rely on id order to decide which of two events came first.

Staff additions

Cut from version one
The registry. Version one takes the worker number from deployment configuration or a StatefulSet ordinal.
Migration path
From auto-increment keys: widen the columns to 64 bits first. Snowflake ids are far larger than any existing value, so old and new ids cannot collide and ordering by id still puts old rows first.
Monitor and page on
Clock offset from NTP per host, calls refused because the clock went back, sequence overflows, lease renewal failures, worker numbers in use out of 1,024.

Multi-tenant SaaS platform

per-customer data isolation

How strongly to separate customers is a pricing decision, so offer tiers: shared tables for small plans, a database each for larger ones, a whole stack for the largest. The engineering rule underneath all three is the same. The tenant comes from a verified token, is set once, and is enforced by the data layer, so that a forgotten filter in application code cannot leak anything.

Requirements and scale

  • 10,000 customers, from two-person teams to banks. The largest is a thousand times the size of the median.
  • One customer must never see another's data. A single leak can end the company.
  • Enterprise buyers ask for a dedicated database, their own encryption key and data kept in their region.
  • A heavy tenant must not slow the others down.
  • The cost of a small tenant stays near zero, and onboarding takes seconds.

Architecture

  1. A user signs in through the identity provider. The token carries a signed tenant_id.
  2. The gateway verifies the token, applies that tenant's rate limit and attaches the tenant to the request.
  3. The router looks up which cell holds the tenant and forwards the request there.
  4. Inside the cell, the data layer sets the tenant on the database session before any query runs. In the pooled tier, row-level security filters every table by it.
  5. The control plane stays out of the request path. It onboards tenants, places them in cells, moves them between tiers and deletes them.

Data model and API

JWT claims   sub, tenant_id, roles, plan             signed by the IdP
tenants      tenant_id -> plan, cell, status, kms_key, region
placement    tenant_id -> cell endpoint              cached at the router

-- pooled tier, Postgres
create policy tenant_isolation on invoices
  using (tenant_id = current_setting('app.tenant_id')::uuid);
begin; set local app.tenant_id = '<from the token>'; ... commit;

-- pooled tier, DynamoDB
PK = TENANT#<id>#INVOICE#<id>
role assumed per request, condition dynamodb:LeadingKeys = TENANT#<id>

The hard part: the same bug, with and without database enforcement

Tenant identity comes from the signed token and nowhere else. A header, a subdomain or a field in the request body can be changed by the caller.

One piece of middleware sets the tenant for the transaction with set local. The setting ends with the transaction, so a pooled connection cannot carry one tenant's identity into another's request. With no tenant set, policies match nothing, so a background job that forgets it sees zero rows.

The same pattern exists outside Postgres. In DynamoDB, put the tenant at the front of the partition key and assume a role per request whose policy allows only that leading key. In S3, do the same with a prefix. The application then cannot reach another tenant's data even with a bug.

Caches, search indexes and queues need the same treatment. A cache key without the tenant in it is the most common way pooled systems leak. Put the prefix in the cache wrapper so that callers cannot leave it out.

Trade-offs

Three tiers: pool, bridge, silo over one model for every customer

Shared tables are the cheapest to run and the quickest to onboard. A dedicated stack costs the most and is what a bank will require. Offering both means small customers do not pay for separation they did not ask for.

Isolation enforced by the data layer over a tenant clause in every query

Hundreds of queries written by many people will eventually include one that forgot. Enforcement in one place makes that mistake harmless.

Cells of a few hundred tenants over one large shared deployment

A bad deploy or a runaway tenant affects one cell. Cells are also the unit for placing customers in a region and for moving a growing one.

A key per tenant in the upper tiers over one platform key

Destroying the key makes that tenant's data unreadable everywhere, backups included. It is the only practical way to honour a deletion request.

Failure modes

  • One tenant floods the API. Its own rate limit and concurrency cap apply at the gateway and in the workers. If it stays hot it is moved to its own cell.
  • A cell goes down. Only the tenants placed there are affected. Recovery and failover happen per cell.
  • A cached response is served to the wrong tenant. This happens when the cache key lacks the tenant. The cache wrapper adds the prefix, and a synthetic check in production requests tenant B's object with tenant A's token and expects a 404.
  • A tenant asks for all its data to be deleted. Pooled tier: delete by tenant id, then verify. Upper tiers: drop the database and destroy the key.

Staff additions

Cut from version one
Bridge and silo tiers, customer-managed keys, cells. Version one is pooled with row-level security, and tenant_id on every row, log line and metric from the first day. Adding it later is the expensive part.
Migration path
Adding enforcement to an existing app: backfill tenant_id, turn on policies in a mode that logs violations without blocking, fix what the logs show, then enforce. Moving a tenant from pool to silo: copy, replicate changes, freeze writes briefly, switch the placement entry.
Monitor and page on
Any failure of the cross-tenant tests, in CI or from the production canary. Per-tenant latency and error rate, each cell's largest tenants by share of load, queries rejected by policy.

Geo-sharded database

for a global app

Give every user a home region, keep all of that user's rows together in a shard there, and route by a key that already contains the region. Local requests are then fast, strongly consistent and legally where they should be. What remains hard is everything that crosses regions: reading someone else's data, writes that involve two users, and moving a user's home.

Requirements and scale

  • 500M users on three continents. Most requests touch only the caller's own data.
  • Reads and writes of your own data complete within 50 ms at p99, wherever you live.
  • European and Indian personal data stays in its jurisdiction, backups included.
  • Losing a zone loses nothing. Losing a region affects only the users homed there.
  • Users move country and regions fill up, so data must move with no downtime.

Architecture

  1. A request reaches the nearest region.
  2. The app works out the home region of the data it needs. The user id carries the region, so the directory is consulted only for users who have moved, and it is cached.
  3. If home is here, the request reads and writes the local shard. Each shard replicates synchronously across three zones.
  4. If home is elsewhere, the request is forwarded to that region's app. Results that are public are cached locally.
  5. Backups and disaster-recovery copies stay inside the jurisdiction, in a second region of the same country or bloc.

Data model and API

user_id = <region: 8 bits><shard: 12 bits><sequence>    routes itself
directory   user_id -> region, shard, version       moved users only
shard map   (region, shard) -> replicas, leader     per region, cached

users, posts, orders ...  all keyed by user_id first    one user, one shard
global_names   username -> user_id     one leader, replicated everywhere

own data, read or write   -> home region, local, strongly consistent
someone else's data       -> forwarded to their region, public parts cached
a write across two users  -> local commit + outbox, applied in the other region

The hard part: moving a user to another region while they keep using the app

The same four steps split a hot shard or drain a full one. Copy a consistent snapshot, replay the changes made during the copy, freeze writes for that user once the lag is under a second, wait for the target to catch up, then flip the directory.

The directory entry carries a version. A server holding the old route sends its request to the old shard, which answers "moved, version 2". The server refreshes its cache and retries. No coordinated cache flush is needed.

The source copy is deleted only after a grace period, and for a move driven by data residency that deletion is the legal point of the exercise. Verify it and record that it happened.

Avoid transactions that span regions. A follow, a message or a payment between users in two regions commits locally with an outbox row and is applied in the other region a moment later, as on sheet 11.

Trade-offs

One home region and one leader per shard over accepting writes for the same row in every region

Each row has a single place where writes are decided, so there are no conflicts to merge and data stays in its jurisdiction. The cost falls on travellers, whose requests cross an ocean.

Region inside the id over a directory lookup on every request

Routing needs no network call for nearly all users, and a directory outage affects only those who have moved.

Synchronous across zones, asynchronous across regions over synchronous replication across regions

Another zone is a millisecond away. Another continent is over a hundred. Few products should pay that on every write.

Building on a database that places rows by region over writing the sharding layer yourself

Spanner, CockroachDB and YugabyteDB can pin rows to a region and move them. In an interview, show that you know what they do underneath, then say you would buy it.

Failure modes

  • A zone is lost. Each shard elects a leader in a surviving zone. No acknowledged write is lost.
  • A region is lost. Users homed there fail over to the in-jurisdiction recovery region and may lose the last seconds of writes. Other regions do not notice.
  • Regions cannot reach each other. Each keeps serving its own users. Forwarded reads fail or serve from cache, and cross-region events wait in the outbox.
  • Two people claim the same username in different regions. Uniqueness lives in one small global table with a single leader. The claim goes there first.

Staff additions

Cut from version one
User moves, global usernames, cross-region recovery copies. Version one is two regions, region in the id, and no operation that spans regions.
Migration path
From a single-region database: add the region to the key with everyone homed where they already are. Stand up the second region, home new sign-ups by country, then move existing users in batches with the procedure above.
Monitor and page on
Latency by region, replication lag across zones and to the recovery region, the share of requests that are forwarded, failed moves, and a nightly audit of rows stored outside their owner's permitted jurisdiction. A rising forwarded share means users are homed in the wrong place.

Webhook delivery

retries and ordering guarantees

You are making HTTP calls to a million servers you do not control, and a share of them are slow, broken or down at any moment. Deliver at least once, retry for days, and keep each customer's failures in that customer's own queue. Ordering fights with retries, so promise it per entity and only to customers who ask.

Requirements and scale

  • 1 billion events a day to about 1M customer endpoints. That is 12,000 a second on average and 50,000 at peak.
  • The first attempt goes out within 5 seconds of the event. Retries continue for 3 days.
  • Every event is delivered at least once. Customers can detect duplicates and order from the payload.
  • Some endpoints are always slow or down. They must not delay anyone else.
  • Customers can see every attempt and replay events themselves.

Architecture

  1. A product service emits an event through its outbox. It never calls a customer directly.
  2. Intake stores the event and finds the endpoints subscribed to that event type.
  3. One delivery is enqueued for each endpoint, on that endpoint's own queue.
  4. The scheduler picks the next delivery for each endpoint, respecting its concurrency cap, its rate limit and the state of its circuit breaker.
  5. A sender takes the delivery.
  6. It signs the body, POSTs it with a 10-second timeout and records the status code and latency. Any 2xx is success.
  7. On failure the delivery gets a next-attempt time from an exponential schedule with jitter.
  8. When the time comes it rejoins its endpoint's queue. After 3 days it moves to dead letters and the customer is notified.

Data model and API

POST https://customer.example/hooks
  X-Webhook-Id: evt_8f3c              same on every retry
  X-Webhook-Timestamp: 1767225600
  X-Webhook-Signature: v1=hmac_sha256(secret, timestamp + "." + body)
  X-Webhook-Sequence: 2               per ordering key
  body: {type, created, data}         2xx within 10 s = delivered

endpoints   id -> url, secrets, event types, ordered?, state, limits
events      event_id -> type, key, sequence, payload          30 d
deliveries  (endpoint_id, event_id) -> state, attempts, next_attempt_at
attempts    (delivery, n) -> status code, latency, error      30 d
POST /endpoints/{id}/replay {since | event_ids}

The hard part: ordering and retries pull in opposite directions

Strict order means a failed event holds back everything after it. Applied to a whole endpoint, one bad event would stop a customer's entire feed for three days. Applied per ordering key, such as the order id, it holds back one entity.

Make it opt-in, and bound it. If the first event exhausts its retries, the key is marked broken and later events for it go to dead letters together, so the customer can replay them in order.

Give every customer the tools to cope without strict order: a stable event id to dedupe on, and a per-key sequence number so that a receiver can ignore anything older than what it already has. For many customers the better pattern is to treat the webhook as a hint and fetch current state from the API.

Per-endpoint queues carry the rest. Each endpoint has a concurrency cap, so a server that takes 9 seconds to answer slows only its own deliveries. A circuit breaker stops attempts after repeated failures and probes once a minute. When the endpoint recovers, the backlog drains at that endpoint's rate limit.

Trade-offs

A queue per endpoint over one shared delivery queue

In a shared queue, one customer whose server hangs fills every sender with their retries. Separate queues with a cap confine the damage to the customer causing it.

At-least-once with an id and a signature over attempting exactly-once

A timeout does not say whether the customer processed the event. Send it again with the same id and let them dedupe.

Ordering per key, opt-in over ordering for every delivery

Most customers want speed and resilience more than order. Those who need order need it for one entity at a time.

Backoff with jitter over days over quick retries at a fixed interval

A server that is down needs time. Thousands of retries arriving together the moment it returns would take it down again.

Failure modes

  • A customer's endpoint is down for a day. Its breaker opens and its queue grows up to the retention limit. No sender time is spent on it. It drains at a controlled rate once probes succeed.
  • A sender crashes mid-request. The delivery's lease expires and another sender retries it. The customer may see the event twice, with the same id.
  • A customer registers an internal address as their URL. The sender resolves DNS, refuses private and link-local ranges, connects to the address it checked, and does not follow redirects.
  • One event matches 100,000 endpoints. Fan-out is itself queued and done in chunks, so it does not stall intake.

Staff additions

Cut from version one
Strict ordering, the replay API, per-endpoint tuning. Version one is a queue per endpoint, five retries over an hour, HMAC signatures and a delivery log.
Migration path
From HTTP calls made inline in request handlers: write the event to an outbox instead and run the new pipeline in shadow, comparing what it would have sent, before switching.
Monitor and page on
Time from event to first attempt at p99, first-attempt success rate across all endpoints, age of the oldest delivery in any healthy endpoint's queue, dead-letter rate. Do not page on one customer's endpoint failing. That is their outage, and the right response is to notify them.

Real-time analytics dashboard

over billions of events

A dashboard asks for totals, and totals can be prepared in advance. Land every event in a durable log, fold events into per-minute rollups as they arrive, and serve charts from a columnar store that holds those rollups. Raw events go to cheap storage so anything can be recomputed. The difficult part is that events arrive late, out of order and twice.

Requirements and scale

  • 10 billion events a day. That is 115,000 a second on average, 500,000 at peak, and about 5 TB of raw data daily.
  • A dashboard tile loads in under a second, over ranges from 15 minutes to 90 days.
  • Numbers are fresh to within 10 seconds.
  • Events arrive late, out of order and more than once, because phones go offline and SDKs retry.
  • A few thousand people view dashboards at a time. Reads are tiny next to writes.

Architecture

  1. SDKs send events in compressed batches, each event carrying its own id and the time it happened.
  2. Collectors validate, stamp arrival time and append to a partitioned log. The log absorbs spikes and lets every consumer go at its own pace.
  3. Stream jobs drop duplicates and assign each event to a one-minute window by the time it happened.
  4. They write rollup rows keyed by window and dimensions to the columnar store.
  5. A dashboard asks the query service for a metric over a range.
  6. The query service picks the coarsest rollup that satisfies the chart's resolution, runs the query, and caches the result for a few seconds.
  7. The log is also archived to object storage as Parquet. A backfill job recomputes any range from the archive and overwrites the affected partitions.

Data model and API

event  {event_id, ts, tenant, type, user_id, country, platform, props}
POST /v1/events     batch of up to 500, gzip        -> 202 accepted

rollup_1m  (tenant, type, country, platform, minute)
           -> count, sum(value), hll(user_id), tdigest(latency)
rollup_1h, rollup_1d   same shape, built from the level below
raw        object storage, Parquet, by date and hour     the truth

GET /query {metric, group_by[], filters, from, to, step}
    -> coarsest rollup that satisfies step; result cached 5 s

The hard part: an event that turns up two minutes late

Bucket by when the event happened, never by when it arrived. Otherwise a phone coming back online after a tunnel shows up as a burst of activity that never took place.

Recent buckets therefore have to be changeable. The stream job keeps the last hour of windows open and tracks a watermark, its estimate of the time up to which everything has arrived. Events later than an hour are left to the nightly recompute from the archive.

Write rollups as "the count for this window and these dimensions is 42", keyed by window and dimensions, and never as "add one". After a crash the job replays from its last checkpoint and rewrites the same rows with the same values, so nothing is counted twice.

Unique users cannot be summed across buckets. Store a HyperLogLog sketch per row instead of a number. Sketches merge across minutes, hours and shards and are accurate to about 1%. Percentiles get the same treatment with t-digest.

Trade-offs

Rollups prepared ahead over scanning raw events for each chart

A day by minute and country is a few hundred thousand rows instead of 10 billion. The cost is deciding the dimensions in advance. Anything else is a slower query against the archive.

A columnar OLAP store over a general-purpose database or a search index

Charts read a few columns of many rows. Column storage, compression and vectorised scans do that hundreds of times faster. Use ClickHouse, Druid or Pinot and do not build one.

Approximate distinct counts over exact ones

Exact unique users needs every id kept forever. A sketch is a few kilobytes and merges freely. Dashboards rarely need better than 1%.

Stream for fresh numbers, batch for final ones over the stream alone

The stream answers in seconds and tolerates an hour of lateness. The nightly recompute fixes the rest and is the way out when a bug is found in the stream job.

Failure modes

  • A stream job crashes. It restarts from its last checkpoint of offsets and state. Rollup writes are idempotent, so the replay changes nothing it already wrote.
  • Traffic jumps tenfold. The log absorbs it and consumer lag grows. Dashboards show a "data delayed" badge driven by the watermark while consumers scale out.
  • A bad release writes wrong rollups for an hour. Replay that hour from the log or the archive and overwrite the affected partitions.
  • A customer adds a dimension with a million values. Per-tenant cardinality limits fold the excess into "other" and flag the tenant. Unbounded dimensions are how these stores fall over.

Staff additions

Cut from version one
The stream processor, sketches, hourly and daily rollups, backfill tooling. Version one is Kafka feeding ClickHouse directly, with a materialised view producing the one-minute rollup.
Migration path
From charts that query the production database: send events to the new pipeline in parallel, compare the two sets of numbers for a week, then repoint the charts.
Monitor and page on
Freshness measured as now minus the watermark, consumer lag, query latency at p95, the daily difference between rollups and a recount from raw, and the share of events dropped as too late. Page on freshness and on the reconciliation difference.

Rewards and cashback engine

that can't be abused at scale

Every grant is money leaving, and people will try to make it leave faster. Treat rewards as a ledger. Each grant is claimed with a unique key so that it can only happen once, reserved against a budget with an atomic check, and held as pending until the refund window has passed. Fraud controls then have time to act before anything can be spent.

Requirements and scale

  • 100M payments a day pass through evaluation. That is 1,200 a second on average and 10,000 at peak, with thousands of campaigns live.
  • A reward shows within a couple of seconds of the payment.
  • A reward is granted once per qualifying event, whatever is retried or replayed.
  • A campaign never spends more than its budget, even in the last second of a rush.
  • People will create fake accounts, collude with merchants and refund after collecting. The design assumes it.

Architecture

  1. A payment completes and its event is published from the payment service's outbox.
  2. The rule engine consumes the event and finds the campaigns it could qualify for.
  3. A fast risk check looks at the device, the payment instrument, the merchant and recent velocity.
  4. The amount is reserved against the campaign budget and the user's own caps with conditional updates.
  5. A grant is written to the ledger in state PENDING: a debit to the campaign account and a credit to the user.
  6. The wallet shows the reward as pending.
  7. The user sees it at once but cannot spend it yet. After the hold period it becomes available. A refund or a fraud finding reverses it with a new ledger entry.

Data model and API

campaigns  id -> rules, start, end, caps {per txn, per user, total}, state
grants     (campaign_id, event_id) UNIQUE -> user, amount, state, risk
budgets    campaign_id -> cap, spent
           update ... set spent = spent + x where spent + x <= cap
user_caps  (campaign_id, user_id, period) -> amount      same update
ledger     entry_id, account, +/- amount, grant_id, reason, ts
wallet     user_id -> pending, available         derived from the ledger

grant states   PENDING > CONFIRMED > REDEEMED      PENDING > REVERSED
POST /internal/evaluate {event}        idempotent on event_id
POST /campaigns/{id}/pause             the kill switch

The hard part: three guards between a payment and spendable money

The grant key is a unique constraint on campaign plus qualifying event, or campaign plus user for a once-per-person offer. A retried request, a replayed event and two workers racing all end in one row. It is the inbox pattern from sheet 11.

The budget check and the spend are one statement: add the amount only if the total stays under the cap. With 10,000 requests racing for the last 500 rupees, the database lets through exactly what fits. Per-user daily and lifetime caps work the same way.

Pending rewards are what make careful fraud detection possible. A fast inline check catches the obvious cases. Slower analysis over the graph of devices, bank accounts and merchants runs afterwards and can reverse a reward any time before it vests.

Tie eligibility to things that are costly to fake: a device, a verified identity, a bank account. Accounts are free to create. And require three caps on every campaign, per transaction, per user and in total, with a global daily burn limit above them all, because the most expensive abuse is usually a misconfigured rule.

Trade-offs

An append-only ledger over a balance column updated in place

Every rupee has an entry and a cause, reversals are new entries, and finance can reconcile to the paisa. A mutable balance loses the history and is easy to corrupt in a race.

Rewards that vest after a hold over cashback that is spendable at once

The hold covers the refund window and gives fraud analysis time. Show the reward immediately so that the product still feels instant.

Eligibility per device and payment instrument over eligibility per account

One person with fifty accounts still has one phone and one or two bank accounts.

Evaluation from the event stream over evaluation inside the payment request

The reward appears a second later, and payments do not depend on the rewards system being up.

Failure modes

  • The same payment event arrives twice. The second insert of the grant key fails and evaluation stops.
  • A campaign is launched with a rule that pays far too much. Validation rejects a campaign without all three caps. If the caps themselves are wrong, the daily burn limit trips, the campaign is paused, and pending rewards are reversed before they vest.
  • A user refunds after spending the cashback. The reversal takes the available balance below zero. Later rewards pay that off first and the account is flagged.
  • The rule engine is down. Events wait in the queue and rewards are late. Payments are unaffected.

Staff additions

Cut from version one
A rule language, graph-based fraud detection, instant redemption. Version one is one campaign type written in code, the ledger, the unique key, three caps and a 7-day hold.
Migration path
From balances held in a column: write a ledger entry beside every balance change, reconcile the two nightly, then make the balance a projection of the ledger.
Monitor and page on
Burn rate against plan per campaign, which is the alarm that matters most. Grants per device and per bank account at the high end, reversal rate, the difference between ledger and wallet, evaluation lag.

Disaster recovery

for a core banking system

Start from two numbers: how much data you may lose, and how long you may be down. For a bank's ledger the first is zero, which forces synchronous replication to a site close enough to be fast. A second, distant site covers the loss of the whole city. Replication does nothing against corruption, so offline backups are a third and separate defence. And failover is only safe if the old primary is stopped first.

Requirements and scale

  • The ledger of a bank with 50M accounts. A few thousand transactions a second at peak, around the clock.
  • Recovery point of zero for the ledger. No committed transaction is lost when a data centre is.
  • Recovery time of two hours or less for critical services, which is what regulators commonly ask. Aim for minutes.
  • It survives the loss of a building, the loss of a city, and the loss of the data itself to corruption or ransomware. Those need three different defences.
  • Exactly one site accepts writes at any moment.

Architecture

  1. Every channel reaches the bank through a traffic switch that points at exactly one site.
  2. The primary site serves all writes.
  3. A transaction commits on the primary ledger.
  4. The commit is acknowledged only after the near site has also written it to disk. This is where zero data loss comes from, and it costs about a millisecond.
  5. The near site ships the log on to a far site in a different region, a few seconds behind.
  6. Full backups and a continuous log archive go to immutable storage, with one copy offline. A restore to a point in time is rehearsed every month.

Recovery targets and mechanisms

tier 0  ledger, payments        RPO 0      RTO 15 min   sync + async
tier 1  channels, cards, ATM    RPO 0      RTO 1 h      warm standby
tier 2  statements, reporting   RPO 24 h   RTO 24 h     restore from backup

commit    primary log write + near-site log write, then acknowledge
far site  log shipping, seconds behind, different seismic zone
witness   third location; a site that cannot see it stops writing
backups   daily full + continuous log archive, immutable, one copy offline
epoch     raised on every failover; writes carry it; an old epoch is refused

The hard part: failing over without creating two banks

A primary that looks dead may only be unreachable. If the standby is promoted while the old primary is still taking deposits from a branch that can reach it, the bank now has two ledgers that disagree, and no rule can merge them. So fence first: cut its storage, block its network or power it off, and confirm.

Fencing should not rely on reaching the failed site. Each site holds a lease from a witness at a third location and stops writing by itself when the lease cannot be renewed. Every failover raises an epoch number, and storage refuses writes that carry an old one.

Transactions caught mid-flight have no final state at the new site. Each is settled by asking the other side, the payment switch or the card network, using the transaction id. It is the same status-check logic as sheet 5.

The technology is the smaller half. A named person declares the disaster, scripts do the steps, and the bank runs from the standby for a full day several times a year. A recovery site that has never carried production has expired certificates, missing firewall rules and half the capacity it needs.

Trade-offs

Three sites: primary, near and far over one distant recovery site

A distant site has to be asynchronous and so loses the last seconds. A near site can be synchronous and lose nothing, but it shares the city's risks. Together they cover a building and a region.

Synchronous replication that falls back to asynchronous over halting when the near site is unreachable

Stopping all banking because a standby link dropped turns a non-event into an outage. Fall back after a short timeout and raise an incident. The cost is a window in which losing the primary would lose data, and some regulators will require the stricter mode.

A person decides, automation executes over automatic failover between sites

False alarms are common, and a mistaken site failover is itself an outage with reconciliation work attached. Failures inside a site are handled automatically. Leaving the site is one human decision and one script.

One writable site over two sites both accepting writes

Two writers on the same accounts need a rule for merging conflicts, and there is no acceptable rule for money. The standby can serve read-only work.

Failure modes

  • The primary site is lost. Fence it, promote the near site, switch traffic. Nothing committed is lost, and service returns in minutes.
  • The whole city is lost. Promote the far site. The last few seconds of commits are missing and are rebuilt from payment network records and channel logs.
  • The sites lose sight of each other while both are healthy. The site that can still see the witness carries on. The other stops writing.
  • A bug or an attacker corrupts the data. Every replica has the corruption within seconds. Restore to a point just before it from the immutable backups, into a clean environment, and replay verified transactions.

Cut from version one
Nothing for the ledger. For everything else, start with restore-from-backup and promote services to a warm standby as their recovery targets are agreed with the business.
Migration path
From backups alone: add the synchronous near copy first, because it removes data loss. Script the runbook next. Then run a planned switch-over in a quiet window and repeat it until it is routine.
Monitor and page on
Whether the near copy is in sync, lag at the far site, days since the last successful drill and the last tested restore, backup failures, configuration drift between sites. Page the moment the near copy falls out of sync, because from then on a failure loses data.

Safe deployments

across thousands of servers

Treat every change as guilty until production says otherwise. Send it to a sliver of the fleet, compare that sliver with the old version running beside it, and widen only while the two look the same. Promotion and rollback are both automatic. All of it rests on one rule for every change: the previous version must still work, because rolling back is the first response.

Requirements and scale

  • 20,000 servers in four regions, running hundreds of services. Thousands of deploys a day.
  • A bad change reaches at most 1% of traffic before it is caught, and is gone within 5 minutes.
  • Nobody watches individual rollouts. Promotion and rollback need no person.
  • Two versions run side by side during every rollout, for hours.
  • Configuration, flags and infrastructure changes are as dangerous as code and take the same path.

Architecture

  1. An engineer merges a change.
  2. CI builds one signed artifact. The same bytes go to every environment, so what was tested is what ships.
  3. The rollout engine deploys the artifact to the next ring. On each host an agent drains traffic, swaps the version, checks health and rejoins.
  4. Every host reports metrics tagged with its version and cell.
  5. The health gate compares hosts on the new version with a same-sized group still on the old one.
  6. A pass promotes to the next ring after the bake time. A fail, or missing data, rolls back every ring touched so far.
  7. The feature itself is switched on later with a flag, for 1% of users first. Shipping code and releasing behaviour are separate events.

Rollout plan and invariants

rollout   id -> artifact digest, stages[], current stage, state
stage     {targets: cell selector, percent, bake: 15m, gates[]}
gate      {metric, compare: canary vs baseline, threshold,
           on_missing: fail}
agent     desired version (pulled) -> drain > swap > check > rejoin
          keeps the previous version on disk; reports version, health

POST /rollouts {artifact, plan}     POST /rollouts/{id}/pause | rollback
invariants   one region at a time
             at most 5% of a cell out of service
             version N and N-1 interoperate, in both directions
             config and flags ship through this same path

The hard part: widening exposure one gate at a time

The gate compares the canary with a baseline group of the same size running the old version at the same moment. Comparing with last week would blame the deploy for a traffic change. It checks error rate, latency at p50 and p99, saturation and restarts, and it fails when there is too little data to tell.

Stages wait because some failures are slow: a memory leak, a cache that expires after an hour, a code path that only a nightly job touches. Arrange for at least one ring to bake through a daily peak.

Rollback only works if version N-1 still runs against whatever N has done. Schema changes are therefore split across deploys: add the new column, write to both, move readers, and remove the old column much later. No deploy may need a simultaneous schema change.

Order rings by how much they can hurt: one host, one zone, the smallest region, then the other regions one at a time. Never two regions together. The engine also refuses to start when the fleet is already unhealthy, unless the change is marked as the fix.

Trade-offs

Progressive rings with automatic gates over deploying everywhere once tests pass

Tests cover the cases someone thought of. Real traffic covers the rest, so show the change to a little of it first. The cost is that a full rollout takes hours.

A canary compared with a live baseline over comparison with history

Two groups running side by side see the same traffic, so the difference between them is the change.

Roll back first, diagnose afterwards over fixing forward during an incident

Rolling back takes minutes and needs no understanding of the bug. It constrains every change to stay compatible with the version before it.

Flags to release, deploys to ship over releasing features by deploying

Code can reach every server while switched off, be turned on for 1% of users, and be turned off again in seconds.

Failure modes

  • The canary gets too little traffic to judge. The gate fails on insufficient data. Route a fixed share of real traffic to the canary so that this is rare.
  • A bug appears only at peak, hours later. Later rings are still baking and their gates catch it. Rollback covers every ring that has the change.
  • Someone pushes a config change around the pipeline. There is no side door. Configuration, certificates and flags use the same rings and the same gates.
  • The rollout engine is down. Hosts keep running what they have. Each agent holds the previous version locally, so reverting a host does not depend on the engine.
